# Backend benchmarks

Benchmarks are reported per backend; forkspace does not turn one backend's result into a
universal claim. Never compare an overlay result to a copy result without naming both backends.

The tables below are generated by [`scripts/bench-report.py`](../scripts/bench-report.py) from
the JSON reports in [`benchmarks/`](benchmarks/), which [`scripts/bench.py`](../scripts/bench.py)
writes. Each run starts from a fresh `FORKSPACE_HOME` and a private copy of the corpus and times
the whole command (CLI startup to exit): `new`; a clean `diff --stat`; `diff` after one edit;
`merge --dry-run`; a one-file `merge`; `ls` with one and five workspaces; and `drop`. Every
command runs with `FORKSPACE_TRACE=1`, so each report also keeps where the time went
(`preflight`, `materialize`, `manifest`, `scan`, `plan`, `apply`, ...). p95 over five samples is
the slowest sample or close to it; shared CI runners are noisy, so compare numbers only within
one report.

Two corpora are used:

- **Next.js:** a fresh `create-next-app@15.5.4` (TypeScript, ESLint, Tailwind, App Router)
  installed with `npm ci` from the lockfile pinned in
  [`scripts/bench-corpus/`](../scripts/bench-corpus/), committed to Git, with a `.env`.
  [`scripts/bench-corpus.sh`](../scripts/bench-corpus.sh) builds and caches it.
- **Synthetic:** one-byte files in directories of 100: a fifth in a Git-tracked `src/`, the rest
  in an ignored `node_modules/`.

The disk line is forkspace's own allocation after one fork (stopping at mount points, so an
overlay counts only its upper layer) and the change in the volume's free space. The freeze line
writes a small file into the project every 2 ms while `new` forks it, against the same writes
with no fork running.

## Measured Linux overlay on a real project

The figures in the README's opening film, measured by hand because they compare with
`git worktree` plus `npm install`, which the script does not run. Intel Core i9-9900K
3.60 GHz, Linux 7.0.0-38-generic, ext4, fuse-overlayfs 1.15, Node.js 23.11.1 and npm 11.14.0,
measured 2026-10-13. The project is a fresh `create-next-app@15.5.4` (TypeScript, ESLint, Tailwind, App Router) after
`npm install`: 324 packages, 20,062 entries and 424 MiB in `node_modules`, committed to Git,
with a `.env` beside it. Times are wall-clock for the whole command.

| Operation | Samples | Result |
| :-- | --: | --: |
| `forkspace new` (fuse-overlayfs backend, one fresh `FORKSPACE_HOME`) | 6 | p50 76 ms, slowest 86 ms (the first) |
| `git worktree add`, copy `.env`, `npm install` (warm npm cache) | 3 | 4.49 s, 4.51 s, 4.82 s |
| `npm install` (empty npm cache) | 1 | 15.44 s |

After a fork, the workspace's upper layer holds 0 bytes; `node_modules` and `.env` are read
from the project. The six workspaces' forkspace metadata took 16 MiB in total. Tests and a
production build ran inside a fresh workspace with no install step.

## Results still requiring release hardware

APFS clone latency, disk sharing, and the freeze test on macOS are **not published as measured
facts** until a report from a Mac is in [`benchmarks/`](benchmarks/). The manual
[`bench` workflow](../.github/workflows/bench.yml) runs the test suite and the same script on
GitHub's macOS and Linux runners and uploads the JSON reports. Linux reflink is O(entries), with
disk sharing verified by the ioctl probe/CI volume job rather than inferred from a filesystem
name.

## Reproduction

```sh
python3 scripts/bench.py --synthetic 10000 --backends auto,copy --out docs/benchmarks/my-host.json
corpus=$(scripts/bench-corpus.sh)   # network on the first run only
python3 scripts/bench.py --corpus "$corpus" --backends auto --out docs/benchmarks/my-host-next.json
python3 scripts/bench-report.py     # regenerate the tables above
```

`--work <dir>` puts the corpus copies and workspaces on the volume you want to measure (the
default is the system temporary directory, which is tmpfs on many Linux hosts). `--short` is the
quick end-to-end check the test suite runs. `FORKSPACE_TRACE=1` works on any command, outside the
script too.
